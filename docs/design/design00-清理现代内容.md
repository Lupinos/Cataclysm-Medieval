# 策划案 000：先建立干净的中世纪荒野基底

## 一、目标与先后顺序

本项目第一步是从当前原版基线中裁剪出**干净、可进入游戏、可维持基础生存循环的中世纪荒野**。完成这一阶段后，才开展新的游戏字段、战斗体系、装备、聚落和其他新资产建设。不得把内容清理推迟到新增系统的开发过程中。

本案确认阶段目标、方案取舍、工具需要回答的问题与验收要求。具体程序接口、解析规则、数据迁移命令和执行进度留到对应 process；本文不是已经完成裁剪或测试的报告。

### 1.1 本阶段应得到什么

- 自然地形、植物、普通动物、季节、天气、昼夜、水源与基础资源能够正常运作。
- 存在符合本阶段目标的最小开局，可以采集、获得饮水和食物、生火、使用基础工具、进行必要制作，并保存和重新进入游戏。
- 现代建筑、车辆、成品、工业生产链以及不属于本阶段的原版灾变内容，不在玩家世界中出现或成为可取得、可制作的内容。
- 实际加载的数据集已裁剪；不再依赖“全部加载现代定义，但设法不生成”作为最终成果。
- 原版中符合需求的植物、材料、食物和基础物资直接复用，不为重新命名或整理目录而重写全部自然内容。

“中世纪荒野”是后续建设的基底，本阶段不据此新定完整世界观、植物物种清单、精确生态参数或装备数值。旧世界观、敌人和战斗文档中未经本分支重新确认的设定，不自动转成这一阶段的要求。

### 1.2 本阶段不做什么

不提前实现新装备库、城镇、奇幻生物和战斗重构；不为裁剪顺便改变通用游戏字段。允许为正常开局、加载隔离、验证和去掉现代内容入口而做必要的最小调整。留下的基础物资优先使用适合的原版定义，不能以等待全部新资产完成为由阻塞荒野基底。

## 二、总体方案：保留原版快照，裁剪唯一工作数据集

采用**可追溯的原版参考＋唯一实际加载的工作数据集＋保留目标驱动的引用分析＋逐批验证**。

| 方案 | 评价 | 本案采用方式 |
| --- | --- | --- |
| 完整加载原版，以黑名单及覆写隐藏现代内容 | 容易快速获得荒野外观，但无用定义仍需解析；长期容易漏入口、积累覆盖和字段兼容成本 | 只作迁移期间的局部辅助，不作为最终数据边界 |
| 完整加载原版，使用现有物品等白名单 | 能缩小允许范围，但仍解析未允许的定义；各系统白名单语义也不同，新资产还需准入 | 可辅助核对和过渡，不能替代数据裁剪 |
| 基于原版工作副本，移除不需要的定义和入口，保留自然及基础功能依赖 | 初期需要整理依赖，但后续只维护实际使用内容，适合代码和字段都将大改的 overhaul | 本阶段主方案 |

“自有数据集”不要求先创建全新的目录或另建一套复杂的模组架构。现有数据目录可以成为项目维护的工作副本；是否采用独立 core 包由后续加载方案决定。最终必须清楚知道玩家启动和测试时加载的是哪份数据。

现有物品过滤在数据加载后执行，不等同于排除 JSON 加载；地图、物品、配方、怪物、NPC、事件等也不能由一张物品名单统一管理。不能继续以“不改原版数据”为绝对限制。

## 三、评估引用分析工具

### 3.1 建立引用图，而不是假设存在一棵完整的树

需要工具帮助定位对象、依赖和删除影响。数据存在共享依赖、循环引用、继承、覆盖、匿名生成器和跨类型关联，应采用可双向查询的图。

约定 `A → B` 表示 **A 使用或依赖 B**。工具至少需要回答：

1. A 定义在哪里、属于什么类型、是否为抽象基类或覆盖；按实际加载顺序生效的是哪份定义？
2. A 直接和间接依赖哪些对象？
3. 删除或改变 B，会影响哪些仍保留的 A？
4. 某对象为什么必须保留，能否展示从保留目标或必要系统到它的引用路径？
5. 某现代物品可能通过哪些地图、采集、掉落、制造、容器、事件或代码入口进入游戏？
6. 哪些关系已被识别，哪些只能视为待确认，哪些引用已经断开？

节点应按类型或实际 ID 命名空间区分，不能把同名 item、item_group 和其他对象混为一体。文件位置与字段路径应能回查；没有普通 ID 的对象也应可定位。一个文件有多个对象时，应能在对象粒度判断保留和移除。

### 3.2 区分不同性质的边

| 关系 | 用途与注意点 |
| --- | --- |
| 定义与加载依赖 | 继承、抽象基类、材料、必需标识等；决定定义能否成立 |
| 物品的附带与转换 | 默认容器、内容物、状态切换、加工结果等；可能引入意外物资 |
| 世界生成与产出 | 地图、地形采集、物品组、怪物掉落、职业、任务、交易和事件等；决定玩家能获得什么 |
| 制作与资源流向 | 配方输入、工具、结果与副产物；保留原料不等于保留所有使用它的现代配方 |
| 代码和隐式入口 | 硬编码 ID、运行时拼接、按注册表枚举、默认选择等；不能只靠 JSON 字符串扫描认定全部覆盖 |
| 表现与可选回退 | 图像、声音、looks_like 等；按实际规则区分必需引用和可选回退，不能都按同一种强依赖处理 |

例如苹果树引用采收表，采收表产出苹果；苹果还可能依赖材料、维生素和加工结果。可直接复用这条自然内容链。现代配方使用苹果，是对苹果的另一个消费者，不应因此自动纳入保留集。

### 3.3 不把工具输出当作“绝对完整”

工具应从明确规则识别引用，而不是把所有与某个 ID 同名的字符串都当成边。静态扫描无法天然证明动态拼接、任意条件分支和 C++ 行为均已覆盖；未识别之处必须可见，不能默认为“没有引用”。

已有定位和物品组工具可以作为起点，但不能把只覆盖物品组的孤立项报告当成全数据依赖分析。优先覆盖即将裁剪的内容及保留链，逐步扩展；不等待一个覆盖所有 JSON 与 C++ 语义的完美分析器才开始清理。

工具首先报告候选、引用路径和影响，由已确定的范围指导裁剪。未经审查的“无引用对象”或自动依赖闭包，不直接成为删除或保留的最终决定。

## 四、评估整体复制、移出原版数据

整体复制本身可作为建立工作副本的方法，但它只提供可恢复的起点，尚未消除任何现代内容。

建议顺序：

1. 固定并记录原版基线提交，确保可以随时比较和恢复。
2. 准备可写的工作数据；原版参考保持只读、位于全部实际加载路径之外。Git 已能保存基线时，不强制把整份原版再提交一遍。
3. 先验证工作数据尚未裁剪时与基线加载行为一致，确认没有漏文件、双重加载或误用参考副本。
4. 在同一份工作数据上逐批裁剪。没有必要先搬空所有数据，再靠不断补文件恢复启动。

“移出工作区”与“移出加载范围”不是同一件事。编辑器隐藏、Git 忽略和在递归扫描目录内另建子目录，都不能作为数据已停用的证据。游戏、测试程序、打包产物均应使用裁剪后的工作数据，禁止因缺定义而暗中回退到完整原版。

在确定加载方案前，不预设必须更换 core ID，也不预设必须维持完整 dda 依赖。需要一起审查基础数据、内容包、额外模组、世界专属数据和测试数据；只移动 data/json 而忽略其余实际加载入口，不算隔离完成。

## 五、评估“从叶子开始裁剪”

不能把叶子作为统一的删除顺序。按本案箭头约定，图的叶子可能恰好是被大量内容使用的钢材或基础物品。

例如：

```text
实验室生成入口 → 实验室物品组 → 现代武器 → 钢材
保留的基础工具 ───────────────────────→ 钢材
```

这里应先去掉实验室入口及不需要的消费者，检查现代武器的其他使用者，再裁剪现代武器的专有依赖；钢材仍需保留。若直接从依赖叶子删除钢材，会破坏本来需要的工具。

采用以下方法：

1. 明确保留目标和必须运作的基础系统，以及本批要排除的内容；另列待确认项。
2. 同时检查“保留目标需要什么”和“拟删除对象被谁使用”，区分定义依赖与玩家获得内容的路径。
3. 优先清理不需要的生成、奖励、制作等消费者和入口；按明确的语义模块裁剪，再检查仅服务于被移除内容的专有依赖。
4. 循环依赖先视为一个关联组审查，不强行套用树的叶子顺序。
5. 对共享依赖保留其必要部分，对混合对象或表做局部删改；不能把一项有用依赖等同于必须保留整套现代模块。
6. 每批结束重新检查剩余引用和实际加载对象，失败则修复本批或回退，不叠加下一批扩大问题。

“没有保留目标可达”是裁剪线索，不是单独的安全证明。按注册表默认出现的对象、反射式查询和硬编码入口，需要明确纳入分析。

## 六、裁剪范围与复用原则

| 类别 | 处理原则 |
| --- | --- |
| 自然地形、植物、普通动物、食物与基础材料 | 尽量复用原版；保留采集、状态变化、掉落和基础加工的完整链，不重写每种植物 |
| 原版基础衣物和工具 | 留下最小可用且符合时代的内容支撑开局与生存，不在本阶段重建完整装备设计 |
| 现代建筑、载具、设备、产品、工业配方和关联事件 | 从实际内容与来源中排除，并清理它们的专有依赖 |
| 混有自然、现代和原版灾变内容的文件 | 按定义和引用分类，不能只凭文件名整包保留或删除 |
| 共享系统、抽象基类、技能标识、伪物品与基础配置 | 按真实必要性审查，不因名称带现代词就盲删，也不因代码出现了某个 ID 就永久保留所有相关内容 |
| 暂时仍被保留功能依赖的现代实体 | 标为未解决项，处理调用方、替代关系或功能范围；不能靠隐藏生成就认定裁剪完成 |

对选入且含义不变的原版对象可保留 ID；确实改变含义才考虑新的身份和迁移。工具辅助批量定位与筛选，不要求人工逐字段重新设计全部物资。

## 七、每批裁剪都实际进入游戏

用户要求的逐步进入游戏验证作为本阶段要求保留。这里的“每一步”指一个可回退、可独立说明目的的裁剪批次；每批通过全部检查前，不继续下一批。批次不能大到一次混改许多互不相关系统，也不要求每删一个 JSON 对象就完整启动一次。

### 7.1 先确立基线

在首次裁剪前确认匹配当前源码和数据的可执行程序、实际加载路径和测试世界。先运行未裁剪基线，记录既有错误；无法启动或缺构建不能视为裁剪造成的预期失败。

### 7.2 每批的验证顺序

| 顺序 | 验证内容 | 不能替代的部分 |
| --- | --- | --- |
| 裁剪前 | 先定义并执行对应行为测试：哪些内容应消失、哪些保留链必须继续工作；确认失败来自目标尚未实现 | 脚本启动失败或缺依赖不是有效的预期失败 |
| 静态检查 | JSON 解析、定义与引用检查，复查本批对象及受影响的共享依赖 | 不能证明实际会生成什么 |
| 游戏加载与一致性检查 | 用实际引擎加载裁剪数据，检查继承、整理及日志错误 | 命令退出成功不等于所有检查通过，也不等于玩家能进入世界 |
| 自动行为检查 | 验证本批禁止来源及保留链；可稳定断言的行为使用可执行测试 | 测试程序若混入完整原版或额外测试资产，不能掩盖正式数据缺失 |
| 实际进入游戏 | 新建测试世界和角色，进入实际地图并执行本批相关操作；保存退出并重新进入 | 主菜单可打开、只载入旧地图或只调试生成物品均不算完成 |

每批的实际入游戏至少确认开局、地图生成和基本行动正常，并实际执行本批影响的采集、掉落、制作、使用或事件路径。具体保留行为及禁止内容由本批范围决定，不把与本批无关的所有装备和系统任意组合穷举。

生成相关检查使用新世界或确认尚未生成的区域；旧存档中的缓存地图不能证明新生成规则正确。保留少量固定种子帮助回归，并在阶段验收时使用多个种子和适用场景，不能用一次没看到现代物品证明它永远不会出现。

### 7.3 失败与完成判定

错误日志、断引用、无法开局、保留行为损坏或禁用内容仍出现，都必须保持本批未完成。不能以补回整套现代数据、永久保留调试入口或扩大白名单来掩盖问题。

实际进入 process 时按 AGENTS.md 先写测试，再实现；记录本批裁剪范围、保留依赖、未解决项、测试条件、命令与观察结果。没有执行实际入游戏，就明确未执行，不得用静态检查代替。

## 八、阶段验收

本阶段完成须同时满足：

1. **加载边界明确**：基线和工作数据可追溯，正式运行不会加载原版参考副本或无关内容包，没有双重加载和隐藏回退。
2. **运行数据干净**：不需要的现代实体及其专有内容已排除；必要系统标识与伪对象有明确理由，不存在靠“理论不可达”搁置的现代实体遗留问题。
3. **来源干净**：地图、采集、掉落、职业、NPC、交易、任务、事件、配方、副产物、容器、转换及实际启用的硬编码路径均按适用范围检查；不把生成屏蔽误作定义移除。
4. **基础生存链完整**：可以正常开局，采集资源、取水进食、生火、使用基础工具并完成必要制作；自然生物与环境变化正常，存档可重新进入。
5. **证据可复查**：相关自动测试、逐批入游戏及阶段多种子检查均有结果；图工具的未知项没有被当作“无引用”忽略，未解决项不被标记完成。
6. **工作顺序守住**：通过这份荒野基底验收后，再进入字段修改、新装备和聚落等后续设计的实现。

旧的五层屏蔽方案不再作为当前主路线，其历史内容可从 Git 查阅。旧调研与技术归档均按 LEGACY 使用；当前测试能力可参考[JSON 测试指南](../vanilla/guide_shared_json_testing.md)，具体行为仍以当前引擎核对为准。
